Auron Business OS — Final QA, Mobile Optimization, Portability & Production Deployment

The current Auron Business OS has been tested through the development environment:

https://92df3d20-9f59-4c6d-96a0-eaa5623b04d3-00-2iqk81shlum4s.pike.replit.dev/dashboard

I have tested the current application on an iPhone.

Before deploying it to production, there are several important issues that need to be addressed.

The application currently:

* Is difficult to use on mobile/iPhone.
* Has UI elements that are not sufficiently mobile-friendly.
* Some functions/features are not working correctly.
* Some workflows need to be more intuitive and user-friendly.
* The application needs a proper functional QA pass before production deployment.

Do NOT simply deploy the current version.

First audit and improve the application, then deploy it.

1. CRITICAL PRIORITY — MOBILE-FIRST EXPERIENCE

The application must be designed and tested primarily for mobile because I will frequently use it from an iPhone.

The desktop version must remain fully functional.

Create a genuinely responsive mobile experience.

* iPhone portrait
* iPhone landscape
* Desktop/laptop

The interface should adapt automatically.

8. DATA INTEGRITY

This is a business application, so calculations must be accurate.

Do not use fake numbers in production.

Do not silently fail when data is missing.

If insufficient data exists, display:

“Insufficient data”

rather than generating an estimated number without clearly identifying it.

Verify all formulas.

Especially verify:

Revenue

minus Direct Event Costs

=

Gross Profit

Gross Profit ÷ Revenue

=

Gross Margin %

⸻

9. CLIENT METRICS

Verify:

Repeat Client Rate

Customer Lifetime Value

Lifetime Revenue

Lifetime Gross Profit

Average Event Value

Average Profit Per Client

Do not calculate repeat clients incorrectly when a client has multiple events.

Avoid duplicate client records where reasonably possible.

⸻

10. CAC / LTV

Verify:

CAC = Customer Acquisition Costs ÷ New Customers Acquired

LTV should preferably be based on historical gross profit rather than only revenue.

LTV:CAC must use consistent methodology.

Clearly display when there is insufficient data.

⸻

11. FINANCIAL LOGIC

Keep these concepts separate:

Revenue

Direct Event Costs

Gross Profit

Gross Margin

Operating Expenses

EBITDA

Net Profit

GST

Receivables

Payables

Do not count GST collected as business revenue where it should be treated as a tax liability.

Do not mix direct event costs with company-level operating expenses.

18. HOSTINGER PORTABILITY — CRITICAL

This application will eventually be moved from Replit to our existing Hostinger Business hosting.

Make the codebase migration-friendly.

DO NOT:

* Hardcode Replit-specific URLs.
* Hardcode Replit credentials.
* Depend unnecessarily on proprietary Replit-only services.
* Store important business logic exclusively in Replit-specific infrastructure.
* Create unnecessary hosting-provider lock-in.

DO:

* Keep frontend, backend, database access and business logic separated.
* Use standard technologies and packages.
* Keep secrets in environment variables.
* Make database connection details configurable.
* Make API URLs configurable.
* Keep authentication portable.
* Keep file/storage paths configurable.
* Keep database migrations available.
* Keep package dependencies documented.
* Keep the project deployable outside Replit.
* Keep the project suitable for eventual GitHub → Hostinger deployment.

Do NOT migrate to Hostinger yet.
